# Waveform queries across doubled project duration

This extends the existing duration cohort to waveform JSON. All six public trials
retain 10,000 actual 100ms occurrences of the same source, with three fresh query
processes per duration in alternating two/four-hour order. Services restart after
authoring. Only project spacing/duration changes; the selected final 250ms contains
150ms of authored gap and the same final source occurrence in both cohorts.

Each cold and 20 cached MCP reads delivers 250 stereo buckets. Every absolute
sample bound, min/max/RMS value and selected provenance matches an independent
source-sample oracle exactly. Repeated artifact hashes also agree. The default
timeline mode and its existing query body remain intact; no waveform image,
spectrogram, model or full-duration PCM is generated by this gate.

The final unchanged gate passes: median sampled service peak is 466,501,632 bytes
at two hours and 427,589,632 bytes at four hours (0.917x). Median growth above fresh
startup is 340,541,440 versus 301,989,888 bytes (0.887x). All six cached p95 values
remain within 250ms, ranging from 146.58 to 233.65ms. Latency includes the public
round trip, delivered JSON and oracle validation; memory samples cover the service
process across cold preparation and cached reads, not the whole process tree or
instantaneous allocation peaks. These observations do not prove native memory
scaling, other query families or immunity to host contention.

## Retained red and owner correction

The original sixth trial passed numerical delivery but failed its cached latency
gate at 301.27ms. Its full samples and artifact remain preserved. Diagnostic memory
arithmetic from those original samples meets the ratio bound, but does not relabel
that original run successful. Concurrent root file hashing is recorded host context,
not an established explanation for the timing failure.

Profiling the same retained cached query found three full revision hydrations per
request. One constructs the actual validated composition; two only establish
ownership for dependency lookup and job pinning. The profile attributes a median
33.93ms to all three revision reads, including 11.52ms inside dependency lookup;
composition/model work and GC remain separately visible in the CPU profile.

`ProjectStore.requireRevision` composes the existing live-project read and bounded
revision-availability check. Dependency lookup and job pinning now use that owner.
The actual composition still reads and validates its document and source context
on every request. There is no model cache, new identity, skipped recovery check or
public API change. An instrumented cached request confirms one full hydration and
the same delivered artifact hash. Timing runs differ in host/observer conditions,
so no causal speedup ratio is claimed. The original six-cohort acceptance gate was
then rerun without profiling and passed all unchanged limits.

Thirteen ProjectStore tests and fifteen service tests pass, including explicit
NOT_FOUND code/message/details/retryable equality for missing, foreign and deleted
ownership. Independent review found no actionable defect. All owned processes
closed; successful trial homes were removed by the existing harness, while the
original failed fixture is retained in the archive after diagnostic reads.

`report.json` is the complete final result. `artifact-files.json` authenticates
complete original/final reports, six delivered JSON artifacts per run, source WAVs,
profile/CPU observations, failed-fixture catalog, tests, source snapshots and review
inside `evidence.tar.xz`. `verification.json` pins the invocation, identities and
archive verification. Run the existing journey with `--query waveform`; omission
continues to select timeline inspection.
