# Ownership rationale

## Editorial control

The [product boundary](../../../README.md#product-boundary) assigns editorial intent
to the external caller. Evidence classification and technical defaults cannot
select an additional operation. The consumer skill teaches practical judgment;
it does not install its recommendations as engine policy.

A convenience expands into inspectable ordinary edits. It is useful because the
caller can review scope and replay the same explicit request; a hidden corrective
treatment would bypass that contract. Development fixtures exercise supplied
operations without turning implementation into an unrequested personal edit.

## One owner per concept

[Composition](../../../packages/composition/README.md) is pure because authoring and
clock algebra have multiple consumers and must mean the same thing across every
interface. [Core](../../../packages/core/README.md) owns durable identity and
transactional lifetime. The [service](../../../apps/service/README.md) coordinates
those owners, while [native execution](../../../helpers/mac/README.md) resolves
physical support and performs the compiled work.

This split prevents protocol adapters and native workers from becoming alternate
edit engines. A processing or synchronization group has its own meaning within
that model; [processing rationale](processing.md) explains why routing, activation,
resampling and state continuity cannot be collapsed into one grouping mechanism.

## Source preservation and fresh storage

The library boundary deliberately refuses incompatible catalogs rather than
inventing missing ownership records or translating old edit history. Existing
media remains intact and can be explicitly admitted as source input. Discovery
must not scan the user's disk and reinterpret every recording as a project.

Capture produces source facts, not an authored multi-video composition. Closure,
canonical publication and managed admission have separate outcomes, so a usable
source need not inherit its sibling's delay. An isolated harness and an installed
app also have separate state; a successful private check cannot prove installation.

## Bounded work and explicit dependencies

Compile requested windows over immutable revisions instead of expanding an entire
movie for a short query. Duration, fragmentation and occurrence cardinality can
grow independently, so output size alone is insufficient proof of bounded work.
Shared job admission gives heavy work one cancellation and publication lifetime.
Every loop must advance or finish with a typed failure; polling cannot repeatedly
restart the work it observes.

Revisions, assets, prepared results and exports retain dependencies explicitly.
Deletion joins those borrowers before retirement; cache eviction cannot remove
original or generated media. Durable tombstones and request identity prevent
retry from resurrecting a deleted project.

[Release acceptance](release-closeout.md) separates delivered behavior from
unmeasured physical, acoustic and contention claims. The original owner-removal
sequence remains in the [historical architecture](https://github.com/dzhng/screen-recorder/blob/c08e0bd8e10903d482232818ccfffaf1d653555a/specs/done/agent-editing/architecture.md);
it is not a second current implementation path.
