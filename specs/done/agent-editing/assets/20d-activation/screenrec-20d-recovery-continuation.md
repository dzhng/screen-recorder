# Candidate: recovery continuation in the existing CaptureService owner

The current service awaits media.recover inside its serialized control order. Raising only the worker deadline would still block cancel/restart and lose the outer response deadline. Native stop already acknowledges finalizing, but absent-native/startup recovery does not have that continuation yet.

Proposed service-owned boundary, for review before implementation:

- Keep one active recovery attempt in CaptureService (recording ID, abort controller, promise), not a new manager, polling worker, or generic task registry. Startup reconciliation processes its existing unsettled list sequentially; only the short start/commit steps use capture serialization. It awaits the current attempt outside that queue.
- Only after native absence is proved (or startup owns stranded recovery), author finalizing using the existing catalog lifecycle. The service can author this state because it now owns durable finalization; source identity and increasing sequence remain mandatory. It does not invent a recording transition or playable support.
- Stop on the same recovering take returns stored finalizing immediately. Stop after an attempt fails can explicitly start one retry; there is no automatic no-progress loop. Recovery completion uses existing settleRecovered/changed. Unknown failure retains bytes and finalizing with a logged actionable typed error; deciding the durable error surface is still necessary, not silently solved by a volatile warning.
- Cancel during recovery requests abort, returns finalizing, and never deletes bytes based on cancellation. After unwind, stop can retry. Explicit library deletion uses existing quiesce and awaits the owned attempt before deleting; it is distinct from capture cancellation.
- Start while recovery owns the capture lane returns a typed retryable refusal rather than entering another capture. Restart cannot claim a replacement started while the old take needs proof; it retains the existing failed-replacement/request-id behavior with an actionable pending code. A later new restart request is explicit. Need confirm this public policy with root.
- Already-settled stop remains idempotent. Completed recovery/report wins cancellation; cancellation cannot change a terminal take to canceled. Absent-native no-source proof remains separate from failed or unreadable decode, and permits deletion only on proven empty allocated source.
- Recovery budget is operation-scoped and includes input bytes plus measured fragmentation work for materialization/export/verification/cleanup of both roles. Reuse publicationDeadlineMs for byte sizing; do not apply source export's 600s allowance as recovery evidence. Actual public worker >30s, responsive finalizing/status/cancel, crash/retry and >10s stop gates are required.

Open design detail: a failed asynchronous recovery needs an actionable public error retained in an existing durable owner; catalog currently has interruptionReason for terminal interrupted, while finalizing cannot pretend failed work settled. Prefer examining existing job/attempt ownership before adding a parallel persistent field. This proposal does not authorize hiding the error in logs or treating a larger client timeout as continuation.
