## Verdict

The core design holds up. I traced the four mechanisms you flagged and three of them are correct as claimed; the defects I found are in the journal's read surface and in what the harness chose *not* to cover.

**Confirmed correct** (so I'm not going to pad the list with them): the bounded handoff (`CursorGeometry.swift:387-408`) is a real counted bound, not a leaky one; the sampler's suspend/resume/stop balance is right on every reachable path — `stop()` re-resumes a suspended source exactly once before cancelling (`:378-382`), and `CaptureWriter.pause/resume/seal/cancel/finish` can't produce an unbalanced suspend; and geometry-epoch retention under delayed readings is sound. On that last one: `forgetSupersededPlacements` (`:291-298`) trims to one placement whenever `pending` is empty, which looks lossy, but every placement's `hostUs` is a frame PTS that is necessarily older than the enqueue time of any reading still to come on the same serial queue, so the surviving placement always covers the next reading. Pause doesn't break it either — `CaptureClock.sourceTime` with `durationUs: 0` admits readings taken *before* `pausedAt` (`CaptureClock.swift:29`), so there's no boundary undercount.

## Confirmed defects

**1. `displaySpace` records are written but unreachable through either reader.** `CaptureWriter.swift:167-173` journals `zeroOriginHeight`, but `CaptureJournal.apply` has no `case "displaySpace"` (falls through `:271`) and `streamCursorEvidence`'s switch handles only `geometry`/`cursorSamples` (`:186-193`). Consumer failure, named: `CursorGeometryProbe.swift:258` is the only real consumer of the evidence stream, so it cannot read the height the take actually flipped through — it instead calls `GlobalPointSpace.zeroOriginHeight()` live at `:377` and `:435`. That is a second independent read of the same quantity, and if the display arrangement changes mid-take the probe validates against a height the recording never used, silently. The README's claim that the height is journaled "so a reading can be re-derived from raw evidence" is only true by hand-parsing the JSONL, not through the API the same README points at.

**2. `streamCursorEvidence` gives the caller no way to learn it stopped early.** `CaptureJournal.swift:176` discards `readRecords`' return and never surfaces `invalidAtSequence`. The commit's claim that streaming "stops at the same boundary the summary stops believing" is true — but stopping is indistinguishable from a short take. Your own test proves the failure shape: `CursorGeometryTests.swift:317-326` gets 1 geometry event, 0 samples and *no thrown error*, and has to make a second full pass via `inspect` (`:320`) to discover why. Every caller now pays two passes over the file to find out whether the first one was complete.

**3. Dead guard at `CaptureJournal.swift:185.`** `apply` sets `summary.lastEvent` unconditionally before returning normally (`:273`), so `guard let event else { return true }` cannot fire. It reads as if some records are unreportable, which is no longer true.

**4. False doc comment at `CursorGeometry.swift:181.`** `sampled` is documented "Readings journaled as samples" but is incremented in `accept` when a reading enters `pending` (`:249`), before the batch reaches the journal. When `record` fails, `CaptureWriter.swift:177`/`:184` drop the batch while the `finished` record still reports the higher count — a consumer diffing `result.cursor.sampled` against `summary.cursorSamples` sees an unexplained gap.

**5. Minor, `CursorGeometry.swift:286`:** `geometryEpoch: placed?.epoch ?? epoch` attributes an `unknownGeometry` sample to a real epoch. Narrow reachability (needs a frame whose `contentRect` attachment is missing at origin), but a reader grouping samples by epoch gets a sample that cites an epoch it was never projected through. `nil` or `0` would be honest.

## Unverified risks

- **`screenRect ?? requestedSourceRect` precedence on display/region capture** (`CursorGeometry.swift:91`). For window capture the lab measured `screenRect` as global top-left, and the README hedges that correctly ("measured on this host"). The next sentence does not: "Display and region captures have no per-frame screen rect, so the request's own global rect explains them" is stated flat and is, by the commit message's own admission, unmeasured. If ScreenCaptureKit *does* populate `screenRect` there and reports it display-local, the new 16 lines of `requestedSourceRect` plumbing in `NativeCapture` are never consulted and every projection on a non-zero-origin display is off by the display origin. `CursorGeometryTests.swift:104` bakes the assumption into a fixture (`screenRect: nil`) rather than proving it. I can't settle this without running native capture.
- `tick()` reads `NSEvent.mouseLocation`/`pressedMouseButtons` off-main (`:399-403`). Commonly done and the lab's 1.49 px result suggests it works, but it isn't documented as thread-safe.
- `startCursorSampling` (`CaptureWriter.swift:99-107`) has no re-entry guard; a second call would drop a suspended `CursorSampler` unreferenced, which is a libdispatch crash on dealloc. Unreachable today (one call site, `NativeCapture.swift:214`), so hardening, not a bug.
- The slice's headline numbers (0.77 / 1.09 / 1.49 px, 1358 samples) point at `/tmp/screenrec-cursor-evidence` "pending integration." Nothing was committed under `specs/recording-for-ai/assets/`, unlike the recovery slice which committed its evidence JSON. Those measurements are currently unverifiable from the repo and the artifacts will evaporate.

## Scope and harness size

Production is ~615 added lines, tests 328, harness (probe + fixture + lab) ~1100. **The size is justified in kind but misallocated.** A pointer-to-pixel transform genuinely cannot be proven without recording real pixels, and the lab is what established the one platform fact the whole design rests on. `CaptureFixture.swift` is a clean extraction, and the probe follows the existing `CaptureProbe` convention in that target — no objection there.

The problem is which half got the cheap tests. The 328 unit lines cover `CaptureGeometry` and `CursorTrack` thoroughly (good asymmetric fixtures at `:46-58`, real epoch-ordering coverage at `:196-210`), but **`CursorSampler` is never instantiated in a test** — the only coverage is the static `skippedTicks` pure function, and the bounded handoff is "verified" by `note(refusedReadings: 7)` at `:251`, a hand-fed literal the sampler never produced. So the two behaviours the commit message advertises most prominently — "the handoff to the capture queue is bounded", "pausing suspends the cadence and sealing ends it" — are the two with no deterministic coverage at either layer, since the lab can't assert on them either. `intervalUs`/`pendingLimit` are already injectable (`:331`), so a headless start/suspend/resume/stop balance test with an interval long enough that no tick fires is cheap and needs no window server. That gap is worth more than another hundred lines of lab.

One documentation correction worth making in the same pass: the README says of the lab "the script only locates blobs and subtracts coordinates," but `cursor-geometry-lab.mjs:299-301` re-derives `scaleFactor * contentScale` to convert the cursor hotspot into output pixels. Small, but it's a second owner of the transform ratio that can drift from `CaptureGeometry`.
